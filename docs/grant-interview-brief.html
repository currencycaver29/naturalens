In parallel we are labeling our own field photos and fine-tuning a small detector so the same loop can later run on-device, offline, and cheap at scale.

Architecture

Two systems, one product

Interviewers often hear “AI wildlife app” and assume one model. We have a product path and a model path. Keep them separate when you talk.

A. What the user touches (alpha)

Phone camera → freeze the still → resize 1024px JPEG → Gemini Flash-Lite (JSON schema) → species + confidence + facts → user saves → AsyncStorage metadata + two JPEGs in the app document directory.

There is no NaturaLens server in this loop. The phone calls Google. Finds never leave the device except the photo bytes sent for that identify call.

B. What we train in parallel (internal)

Field photo → Skim upload (EXIF-normalized, sha256 id) → R2 + D1 boxes → Create run (immutable manifest) → Colab SSDLite train → metrics / preds / TFLite back to R2 → review failures → relabel.

This loop is polar-bear detection (bounding box), not yet the multi-species namer in the phone. Gemini still answers “what species is this?” for testers.

Why cloud ID now

We can leave Expo Go now: Apple Developer + EAS produces a real iOS binary (and can include custom native modules later). Cloud ID is still the right call because the custom detector is not wired, the dataset is not at the switch bar, and we can iterate the product loop without freezing a model.

Why on-device later

Cloud on 4G is typically 2–9s, not <1s. It needs signal, costs per call, and sends photos off-device. A field tool that dies without LTE is a compromised field tool. On-device + cloud fallback is the destination.

Species facts ride the same call. Older saved finds without facts are backfilled with a text-only lookup when opened — facts follow from the label, not the pixels. Location could never be backfilled that way, which is why we have not added GPS yet without a plan.

The ML question

Are you training a model?

Short answer: The app testers use is not running our weights. We are fine-tuning a small pretrained detector on our polar-bear photos. We are not training from scratch and we are not fine-tuning CLIP or ResNet for the product.

Architecture

ItemChoice
FamilyOne-stage object detector, not a classifier-only head.
NetworkSSDLite320 + MobileNetV3-Large (torchvision).
Classes2: background + polar_bear.

OptimAdamW, lr 1e-3, weight decay 1e-4, cosine annealing, grad clip 10.
Default run30 epochs, batch 4, seed 13.
AugmentHorizontal flip, scale-and-pad, brightness/contrast.
MetricmAP@0.5, plus precision/recall at score 0.3. Not “accuracy.”

EfficientDet-Lite via MediaPipe Model Maker is the planned mobile fallback, blocked today because it wants TensorFlow <2.16, which has no Python 3.12 wheels. Say “SSDLite now, EfficientDet-class if we need a smaller mobile graph.”

Labeler

How labels get into the model

Store

  • Images: Cloudflare R2 bucket.
  • Boxes / review flags / run metadata: D1.
  • Primary key is sha256 of the normalized JPEG — duplicates do not fork the dataset.

Integrity

  • Optimistic version → 409 on conflict.
  • Append-only label history.
  • EXIF orientation fixed once at upload.
  • Training run copies an immutable manifest. You cannot silently edit the set mid-train.

Cost control

  • Hard caps at 80% of R2 free tier (8 GB, 800k Class A, 8M Class B).
  • Max object 20 MB. Over cap → HTTP 429.
  • Colab reports S3 ops so Worker + GPU share one meter.

Photos are ours (field captures), not licensed stock. Later species facts: GBIF / IUCN open data. Do not budget photo-library licenses.

Q & A bank

Questions they actually ask

What problem are you solving?

Field identification is either slow (guides, experts) or locked to apps that need an account, a community, or a live model download you cannot iterate. We want a fast personal loop: point, name, keep. Conservation and education only work if the tool is used in the places with bad signal — which is why on-device is the end state, not a slogan.

Who is the user?

Near term: closed testers and field partners who will photograph wildlife and correct us. Polar bear is the first detection class because the team can collect and label it. Consumer “what bird is that?” is the same loop at larger taxonomy later.

How do testers install the app?

iOS: Apple Developer is enrolled. We build with Expo EAS and invite testers on TestFlight — a closed list, not the public App Store. Android: Play Console is not enrolled yet; those testers still use Expo Go or a local build. Do not say the app is “on the App Store.”

Why not just use iNaturalist / Seek / Google Lens?

Seek is the existence proof that on-device vision plus geo ranking works — we say that in our own notes. We are earlier: a simpler personal log, our own labeled field data, and a path to region packs (species priors by location/season). We are not claiming we beat Seek’s model today. We are building the capture → label → train loop we would need to own the model instead of renting Gemini forever.

Is this scientifically valid identification?

No. It is an assistive namer with self-reported confidence, not a taxonomic authority. Conservation status is an enum the model fills; we fall back to Data Deficient rather than invent a Red List row. A future GBIF/IUCN join is how we stop asking a language model to be a database.

What is novel here technically?

Do not oversell novelty. The novel-for-us work is the closed loop: product in the field, our own boxed photos, immutable train runs, failure review, export to TFLite. The architectures (Flash-Lite, SSDLite) are known. Grants fund execution and data, not a new paper architecture.

Why polar bears first?

One class, visually distinct in many frames, conservation story, and a dataset we can actually label. Similar-species pairs (polar vs brown) are a later, harder milestone and need more images per class. Starting multi-species at 10k classes is how you never ship.

How will you know the custom model is good enough to replace Gemini?

Not a single accuracy number. All of: precision/recall per critical class, stable performance in hard conditions, on-device latency under one second on target phones, then a staged rollout (10% → 50% → 100%) with Gemini still as fallback when confidence is low.

What if Google changes pricing or shuts the model?

That is exactly why we are not building the company on a forever Gemini bill. Alpha uses it as a scaffold. The labeler and SSDLite export are the off-ramp. Short term we put a spend cap on the Google project and treat HTTP 429 as a normal user-facing “slow down” state — free-tier limits are already tight.

Why Cloudflare instead of AWS?

The surfaces we have today (site, waitlist, labeler, object store) fit Workers + D1 + R2 at essentially free-tier cost. We do not have a GPU cluster or a multi-service VPC to justify AWS. Training uses Colab or a laptop GPU. We will rent GPU hours when a run needs them — not run idle instances for a grant report.

How do you handle bad or malicious labels?

Internal tool, allowlisted emails, PIN + lockout. Versioned boxes, append-only history, reviewed flag. Architecture notes also call for an admin queue before user-corrected labels enter training — that user-facing confirm/correct UI is not in the phone yet, so we are not claiming citizen labels as ground truth today.

What’s the biggest technical risk?

Three: (1) Gemini key in the client until we proxy it — TestFlight is still a closed list, not a public link. (2) Dataset too small / too clean, so mAP on our val set lies about field performance. (3) TFLite is not in the binary yet. EAS can ship it; the model has not cleared the switch bar.

Do you have tests / CI?

CI typechecks the mobile app on main. There is no test runner. Say it if asked; do not volunteer it as a strength. Grant engineering time can include a holdout eval harness — we already dump per-image TP/FP/FN for the labeler overlay.

Open source? Will the model be public?

Code is MIT. Field photos and weights are not in git. We have not committed to releasing weights. Do not promise a public model unless the grant requires it — then we can, with license on the weights separate from the app.

How will you measure success in 3–6 months?

Product: testers on TestFlight complete capture → identify → save without 429s; Gemini key proxied off the phone. Data: labeled polar-bear set grown toward the 1k+ target; val mAP tracked per run, not a one-off notebook. Model: TFLite artifact timed on a real phone via an EAS build, even if Gemini is still the default.

Ops they may call “production-readiness”

What the user sees when it fails

FailureCopy in the app
Network / fetch rejectYou’re offline. Connect and try again.
HTTP 429Too many photos too quickly — wait a moment and try again.
403, or 400 with “api key” in the bodyYour Gemini API key was rejected.
5xxGemini is having trouble right now.
Anything elseCouldn’t identify that photo. Try again.

A 400 is not automatically a bad key — a malformed request is also 400. We check the body. Fetch only rejects on network failure; 4xx/5xx still resolve. That is why “you’re offline” is safe in the catch.
